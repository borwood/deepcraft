# 0064 — A rule in a docstring cannot fail a build

*2026-07-22 · dc-worldgen · pure refactor, zero behaviour change*

> blogworthy: the difference between a property you *check* and a property you
> *cannot violate* — and how a bug's remedy can be the tell that the design is
> wrong.

## What we were left holding

journal/0063 split `providers.rs` into a module directory, and the code motion
shook out a latent bug (corrections #32). `Providers::default().is_identity()`
returned **false**, naming `outcrop_at`. Nothing had changed about what the
code computed; what changed was how many codegen units it was compiled into.

The mechanism, briefly, because it is the whole reason this entry exists.
`Providers` was four `fn` pointers, and "is this slot the identity?" was
answered by casting the slot's pointer to `usize` and comparing it against the
same field of `Providers::default()`. `identity_outcrop_at` was a `pub use` of
`lithology::exposed_litho`, which is `#[inline]`. rustc may instantiate an
`#[inline]` function once per codegen unit, and each instance has its own
address. Two `Providers::default()` values built in two codegen units held two
different addresses **for the same function** and compared unequal.

It had been green on `main` for the same reason it stopped being green: in the
flatter file the optimizer saw both sides of the comparison in one view and
folded the answer to `true`. The assertion was passing for a reason unrelated
to the property it asserted, and a refactor that moved no values changed the
inlining and exposed it.

0063 fixed it correctly: a plain non-`#[inline]` wrapper in the slot's own
module, plus a new rule written on that wrapper — *a slot's identity must be a
plain, non-inline function defined in this module; never a `pub use` of someone
else's function, whose inlining attributes are not ours to control.*

That is a good rule. It is also a rule in a docstring, and **a rule in a
docstring cannot fail a build.** The next slot conversion is written by whoever
is converting that slot, six months from now, possibly by reaching for the
obvious `pub use`. The check would then silently mis-report, and the failure
would be invisible until something depended on it.

Something now does. The user ratified the same day that **the resolved provider
table is part of world identity** (ARCHITECTURE.md § *Provider seams*): a world
generated with a provider and one generated with that provider's identity
fallback are different worlds, the manifest records which, and loading
hard-refuses a mismatch. A mis-report there is a spurious refusal to load a
perfectly good world — or, in the folding direction, silently accepting a save
generated by providers you no longer have.

So the question stopped being "is the address comparison correct today" and
became "why is a load-bearing fact about world identity being *inferred* at
all?"

## The change: absence becomes a shape

Each slot went from `fn(..) -> T` to `Option<fn(..) -> T>`, and **`None` means
identity**.

```rust
pub struct Providers {
    pub wave_energy: Option<fn(WaveCell) -> f64>,
    pub depth_to_water: Option<fn(WaterPass<'_>, &mut Vec<f32>)>,
    pub parent_p: Option<fn(ParentCell) -> f64>,
    pub outcrop_at: Option<fn(Option<&DepUnit>) -> Litho>,
}
```

`Default` is now derived — all-`None` — which reads better than the old list of
four identity function pointers, because the honest statement about a
default-constructed provider set is *nobody has supplied anything*, not *four
particular functions are installed*.

`non_identity_slots()` becomes `Slot::ALL.iter().filter(|s| self.is_supplied(*s))`,
where `is_supplied` is an exhaustive `match` over `.is_some()`. The `address()`
helper is deleted. No address is taken anywhere in the crate.

The identity functions stay public, and are still called — by the accessors.
One per slot, sharing the slot's name, so the call sites did not change shape:

```rust
// before
let outcrop_at = cfg.providers.outcrop_at;
let l = outcrop_at(top);

// after
let providers = cfg.providers;
let l = providers.outcrop_at(top);
```

`x.outcrop_at` is the field; `x.outcrop_at(top)` is the method. Rust resolves
those without ambiguity, and the result is that the `Option` is invisible
outside `providers/mod.rs`. There is exactly **one** `None`→identity dispatch
point per slot, which is what keeps the byte-identity argument short: the `None`
arm calls the same function with the same arguments as the pre-change code, and
there is only one place to check that.

`erosion.rs` hoists `let providers = cfg.providers;` where it used to hoist a
bare pointer — `Providers` is still `Copy`, and an `Option<fn>` is a null-pointer
optimised word, so the struct is the same four words it was. `BioticSim` now
stores the whole `Providers` instead of one pointer field, for the same reason.

## The rule did not get enforced; it stopped existing

This is the part worth keeping. The obvious response to corrections #32 is
"write a test that asserts every identity function is non-`#[inline]`" — which
is not expressible — or "write a lint", or "put it in the review checklist".
All of those *enforce* the constraint.

The `Option` **retires** it. An identity may now be `#[inline]`, a `pub use`, a
generic instantiation, anything: its address is never taken, so nothing about
its codegen can be observed. The docstring section on `identity_outcrop_at` that
carried the rule has been replaced with a short account of why the rule no
longer applies, and the wrapper survives for a different and much weaker reason
— it gives the identity a name inside the slot's own module, which is what the
module layout is for.

The general form: **when a bug's remedy is a rule humans must remember, that is
evidence the design is inferring something it should be representing.** The
address comparison was asking the compiler a question the compiler does not
promise to answer (`fn`-pointer address uniqueness — guaranteed in neither
direction, and both directions had now been observed). The `Option` asks a
question the compiler cannot get wrong.

## Is the failure mode now impossible by construction?

Yes, and it is worth saying precisely why rather than just asserting it.

The #32 family of failures needs an *address* to exist in the answer. Both
directions — identical-code-folding merging two distinct functions onto one
address, and per-codegen-unit instantiation splitting one function across
several — are properties of where a function lands in the binary.
`non_identity_slots()` no longer reads a function's address, or its identity, or
anything about it at all. It reads whether a discriminant is `Some`. That is a
value stored in the struct at construction, in the same compilation, by whoever
built the set; it round-trips through `Copy` and through `DeepConfig` unchanged,
and no optimizer transformation can alter it without altering the program's
meaning.

So the strongest available test is not a falsifier — it is a pin. Two of them
were added:

- `providers_set.rs::a_default_set_that_cannot_be_constant_folded_still_reports_no_slots`
  reproduces #32's *exact* conditions — the set is built in a separate crate
  (an integration test is its own compilation unit, which is where the two
  addresses came from) and passed through `std::hint::black_box` behind an
  `#[inline(never)]` boundary, so nothing can be folded at the assertion. This
  is the shape that failed under the address comparison. It cannot fail now,
  which is the point; it stands as an executable statement of what used to
  break.
- `providers/mod.rs::the_none_path_is_the_identity_function` states the
  byte-identity claim at the dispatch point instead of only at the far end of a
  17-second world build: for every slot, the accessor on a default set and the
  identity function agree bit-for-bit.

One semantic shift, deliberate and pinned by
`explicitly_supplying_the_identity_function_still_counts_as_supplied`:
`Some(identity_outcrop_at)` now reports the slot as **supplied**. Under the
address comparison it would have reported identity. The new answer is the more
honest one for a manifest — the question a save file asks is *"did an heir
answer this?"*, not *"does the answer happen to equal the old one?"*. Only the
first is decidable, and conflating them is what got us here.

## Evidence

Byte-identity, unchanged and unrelaxed: the pre-slice goldens
`surface 0x7B8968FD90E04062` / `record 0xA53BD77F769D7FF4` pass, captured from
pre-slice `main` (`2434f37`), not from a post-change self-comparison. The
`depth_to_water` agreement test —
`the_materialized_proxy_plane_agrees_with_the_inline_proxy`, which drives the
whole production world down the *materialized-plane* arm with a provider that
reproduces the inline proxy exactly — also lands on those goldens, so both arms
of that seam are still proven and the `Option` dispatch perturbs neither.

corrections #32 gains a **superseded** note: the remedy it records (the
non-inline wrapper rule) is no longer the mechanism keeping the check honest.
The falsification itself stands — `fn`-pointer addresses are not stable in
either direction, and that fact is exactly why the design changed.
